## PDF (pdfplumber·pypdfium2 위에 재구현)

`score_pdf.py` — 실제 보도자료·서식 PDF 18건, 같은 문서 HWPX 글을 정답으로.
rec/prec 는 글자 다중집합, order 는 낱말 순서 유사도, lost 는 정답의 서로 다른 낱말(2자 이상) 중 출력에 없는 수.

| | rec (평균) | prec (평균) | order (평균) | lost (합) |
|---|---|---|---|---|
| memento (PyMuPDF) | 0.805 | 0.874 | 0.701 | 39 |
| new | 0.806 | 0.929 | 0.765 | 7 |

- new 의 lost 7 은 각주 표시가 붙은 낱말(`’25년1」`)이 띄어져 나온 것 등 낱말 경계 차이. 글 자체는 있다.
- 법령 서식 3건은 두 파서 모두 rec 0.05~0.4 인데 측정 착시다. 큰 병합 칸이 많은 서식이라 정답(HWPX)의 병합 칸
  채움이 글을 부풀린다(사업장현황신고서: 채운 격자 42,817자, 실제 칸 글 1,873자, PDF 출력 1,965자). lost 는 0~1.
- 속도: 22건 합계 new 172s, memento 약 200s (그림 설명 끔, 한 프로세스 순차).
- 합성 PDF 32건 오류 없음, 스캔 쪽만 OCR 콜백 호출(s15 1회, s16 1회).

PDF 구현에서 정한 것과 근거:

- **표 소유는 줄·칸 단위.** 블록 단위로 "가운데가 표 안이면 표의 몫"으로 가르면, 표 밑 각주가 표 칸 글과 한 블록으로
  묶여 통째로 버려졌다(lost 173 → 2).
- **찾은 표의 바깥 틀을 가상 선으로 닫고 다시 찾는다.** 공공 문서 표는 바깥 세로 테두리를 흔히 생략해, 가장자리
  칸(행 이름 열, 끝 열)의 모서리가 닫히지 않아 칸이 사라졌다.
- **하위 행은 여러 행에 걸친 칸으로 이어진 행 묶음 단위로 나눈다.** 한 열만 행마다 선이 있으면 행이 잘게 생기고,
  큰 칸이 그 행마다 복사돼 같은 글이 여러 번 나왔다(국세수입 표: prec 0.571 → 0.972, 전망 열 값 복원).

## PDF 격차 줄이기 (2026-10-19)

튜닝용·평가용을 먼저 나눴다(`pdf_split.py` → `pdf_split.json`, 튜닝 전에 한 번 만들고 고치지 않음).

- 시간(같은 PC, CPU 경쟁 없을 때): 규칙 유무는 PDF 150개 92.6/91.9초(끔) vs 95.0/91.1초(켬)로 차이 없음.
  레이아웃 콜백은 olmOCR 98쪽에 콜백 없이 13.2초, GPU(RTX 4070 SUPER) 24.1초, CPU 121.7초. docling 같은 98쪽 GPU 162.5초.

**결론**: 규칙을 기본으로 넣는다(비용 없음, 두 셋 모두 회귀 없음). 레이아웃 모델은 기본 의존성에 넣지 않고 `layout`
콜백으로 둔다. 영문·한 쪽짜리·선 없는 표 문서에서는 크게 오르지만(olmOCR +21.5%p), 주 대상인 한국 공공 문서 표는
dev 0%p·holdout +2.5%p 에 그치고 torch(약 2GB)와 GPU 가 있어야 빠르다. 한국 PDF 표의 남은 격차(칸 어긋남 349)는
레이아웃이 아니라 괘선 표 안 칸 나누기 문제라 다음 과제다.

## 한국 PDF 표 개선 · Camelot 비교 (2026-10-19 오후)

받았다(korea.kr 2024년 12월 통계·조사 보도자료 15건, `collect_real2.py --set real4`, 표 시험 899개, `pdf_split.json` ko-pdf
fresh). 튜닝은 real·real2·real3 만 보고 real4 는 마지막에 한 번 쟀다. 기존 표 시험 4,949개는 그대로 두고 뒤에 붙였다(시드 같음).

  태그만 지우게 고치고 모든 파서를 다시 채점했다(docling 등 다른 파서 재현율도 조금 바뀜).

## 영문 기본 모드: 가로선만 있는 표 (2026-10-21)

olmOCR 에서 기본 모드가 모델 모드보다 낮은 이유(dev, `pdf_fail_classes.py`): 머리말 남음 229(모델 46), 표 미검출 207(모델 12).
다단 순서는 기본이 같거나 높다.

- 머리말: olmOCR 문서는 dev 360건이 모두 1쪽이다. 머리말 제거가 여러 쪽 되풀이에 기대므로 한 번도 켜지지 않는다.
  남는 것은 쪽 번호·학술지 이름·"Downloaded from …" 류. 손대지 않았다(위치·모양 휴리스틱이 제목을 지울 위험).
- 표: 못 찾은 45문서 대부분이 가로선만 있는 논문식 표. 첫 단계가 격자에서 시작해 표로 안 잡혔다.

영문 표 벤치를 더했다: ICDAR 2013 표 대회 67건(EU·US 정부 문서, 글 레이어 있는 PDF, `gt_from_icdar.py` 정답)에서 한국 표와
같은 방식의 표 시험 1,123문항(`icdar_bench.py --build`, `pdf_split.json` "icdar" 이름순 번갈아 dev 34 / holdout 33).
olmOCR-Bench 는 OCR·VLM 변환기용으로 만든 것이라 이쪽이 글 레이어 PDF 파서에 맞다.

| 기본 모드 | 전 | 후 |
|---|---:|---:|
| ICDAR 표 dev (34건, 516) | 51.7% | 75.8% |
| ICDAR 표 holdout (33건, 607, 한 번) | 41.8% | **66.9%** |
| olmOCR 표 dev / holdout | 29.6% / 34.3% | 37.2% / 36.9% |
| olmOCR 평균 dev / holdout | 47.8% / 48.3% | 50.3% / 49.2% |
| olmOCR 다단 dev | 71.1% | 71.1% |
| 한국 표 튜닝용 37 / real4 / real5 | 88.3% / 86.1% / 84.9% | 같음(바뀐 문서 없음) |

같은 코드의 모델 모드(레이아웃 + TableFormer, GPU 작업 2개, 67건 143초): ICDAR dev 80.0%, holdout 83.5%.
영문 표는 기본 모드가 여전히 holdout 에서 16.6%p 뒤진다(선이 하나도 없는 표 등).

- 첫 판은 2단 본문 한 줄(왼쪽 단 + 간격 + 오른쪽 단)을 열로 보고 표가 본문을 삼켜 olmOCR 다단이 2문항 떨어졌다.
  덩어리 둘이 모두 표 폭 35% 넘으면 2단 본문으로 본다.
- 같은 높이 선이 조각(51~125, 125~550)으로 그려지고 머리 아래 짧은 선(cmidrule)이 섞여, 선 끝이 같은 것끼리 묶으면
  표 셋을 가로지르는 엉뚱한 묶음이 생겼다. 조각을 먼저 잇고 겹치는 선끼리 묶는다.

## 벤치 기준 고침과 하위 행 나누기 (2026-10-22)

벤치 기준을 세 가지 바꿨다(`document_parser_cmp/`). 이 절의 숫자는 바뀐 기준이고, 위 절들의 표 시험 숫자와 직접 비교하지 않는다.

## DP-Bench 표 규칙 (2026-10-22)

DP dev 정답 표마다 우리와 kordoc 을 맞대(`ai_table/dp_pages.py`, `dp_show.py`) 남은 실패를 고쳤다: 안쪽 세로선이 위아래로 더
뻗은 표(윗선 없는 머리행·아랫선 밑 합계 행), 그림 제목 한 행·막대그래프 숫자 격자는 표 아님, 같은 색 줄 음영, 선 없는 머리칸
나누기, 선 없는 표 위 머리 줄과 빈 칸 있는 행, 한 쪽에 쌓인 세 줄 표의 폭과 cmidrule 끝, 칸 친 한 열 목록.
공식 `evaluate.py`(`dp_bench.py`), 실패 쪽은 빈 출력으로 넣은 kordoc(`kordoc_fair`)과 비교. holdout 은 고친 뒤 한 번 쟀다.

### 이어서: holdout 까지 튜닝 (2026-10-22)

공개 비교용이라 holdout 실패도 열어 보고 고쳤다. **DP-Bench 는 이제 200쪽 모두 튜닝용이다**(평가용으로 쓰지 않는다).
더한 규칙: 줄무늬 행 표 잇기, 두 행 걸친 머리칸 배경, 선 친 차례·누운 축 글자·숫자만 든 그래프 격자는 표 아님, 위·아래 선
둘뿐인 표(행은 줄 사이 틈), 세 줄 표 안 강조 행·제목칸, 2단 본문 판정에 글자 수, 세로선으로 분류된 가는 가로선, 선 친 표 위
선 없는 머리 줄, 표 제목 문단에 붙은 머리 줄, 글머리표 뒤 틈, 어긋난 칸 배경의 가는 빈 칸. AI 모드에는 규칙과 같은
'표 아님' 판정(`AI_FILTER=1`)과 "표 있나" 문턱 0.99(`AI_GATE`)를 더했다. 문턱은 실제 표 쪽 P(yes)가 세 번 모두 1.0, 거짓 표가
났던 쪽이 0.0~0.98 사이로 흔들려서 정했다(0.5 문턱에서는 같은 설정 두 번이 F1 97.2 / 94.6 으로 갈렸고, 0.99 에서는 두 번 98.1).

## 표 출력 형식 (2026-10-16)

LLM 에 넘길 표를 어떤 형식으로 낼지. `table_format_qa.py`, `table_format_paired.py` — parser-bench `hand_qa` 1·2차의
표 76개(병합 있는 표 70) · 질문 280개. 원본 HWPX 표를 병합 정보째 가져와 형식만 바꿔 같은 질문을 묻는다.

| 형식 | Qwen3.8-27B-FP8 | luna | 표 토큰 합(cl100k) |
|---|---|---|---|
| markdown (병합 칸 값을 덮인 칸마다) | 265/280 (94.6%) | 279/280 (99.6%) | 59,835 |
| markdown-first (첫 칸에만) | 262/280 (93.6%) | 274/280 (97.9%) | 53,878 |
| html (rowspan·colspan) | 254/280 (90.7%) | 276/280 (98.6%) | 84,699 |

- 짝 비교(한쪽만 맞힌 질문, 부호 검정): Qwen3.8 에서 markdown 만 맞힘 16 / html 만 맞힘 5, p=0.027.
  html 의 오답은 대부분 옆 열 값을 읽은 것(colspan 을 세어 열 위치를 잡아야 한다). luna 는 차이가 유의하지 않다
  (3/0, p=0.25). markdown-first 는 두 모델 모두 markdown 보다 낫지 않았다(Qwen3.8 4/7, luna 0/5).
- 공개 연구(TableEval, TeleTables, RealHiTBench, SUC)는 14~32B 모델에서 HTML 이 마크다운보다 1~3점 앞선다고
  보고했지만, 마크다운에서 병합 칸을 어떻게 적었는지 밝히지 않았고 한국어 표는 없다. 우리 표·모델에서는 재현되지 않았다.
- 결정: 기본은 `markdown`. 다른 형식은 `Document.to_markdown(table_format=...)`, CLI `--table-format` 으로 고른다.
- 한계: 질문셋의 표는 대부분 통계표다. 큰 병합 칸이 많은 서식에서는 `markdown` 이 글을 크게 부풀린다
  (사업장현황신고서: 채운 격자 42,817자, 실제 칸 글 1,873자). 서식의 정답률은 재지 않았다.
